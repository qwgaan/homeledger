## 一、这是什么项目

自托管家庭记账系统。**纯后端服务端渲染**架构 —— Node.js + Express + EJS + `node:sqlite`，**只有 3 个运行时依赖**（ejs / express / express-session，合计 80 个包，零原生编译）。没有前端框架、没有构建工具，图表是服务端生成 SVG。

设计取向很明确：**家庭内部多人共用，数据完全自持**，跑在 NAS / 飞牛 fnOS 上。

## 二、架构与数据流

```
server.js（入口：初始化 → 中间件 → 路由挂载 → 优雅关闭）
  ├─ src/db.js           数据层：建表 / 种子 / 预编译语句缓存 / 余额重算引擎
  ├─ src/lib/
  │   ├─ auth.js         scrypt 哈希、SQLite 会话存储、RBAC、CSRF、审计、通知
  │   ├─ txn.js          交易读写 + 统计聚合（记账内核）
  │   ├─ ai.js           双引擎：大模型 + 关键词规则兜底
  │   ├─ attachments.js  账单截图落盘与关联（网页端与开放 API 共用）
  │   ├─ subscriptions.js 订阅周期生成 / 月均摊平 / 到期提醒
  │   ├─ importers.js    支付宝·微信·通用 CSV 解析入库
  │   ├─ charts.js       服务端 SVG 图表
  │   ├─ scheduler.js    每日 + 每 30 分钟兜底轮询
  │   └─ util.js         金额 / 日期 / 转义
  ├─ src/routes/         11 个路由模块
  └─ src/views/          EJS（layout 二次渲染机制）
```

### 值得肯定的几个设计

1. **零原生依赖** —— 用 Node 22 内置的 `node:sqlite`（`DatabaseSync`），不需要 better-sqlite3 的编译链。`Dockerfile` 里 `npm install` 永不失败，这是家庭 NAS 部署最省心的选择。
2. **零依赖 layout 机制**（`server.js:130-147`）—— 视图先渲染成 body 再套进 `layout.ejs`，用中间件劫持 `res.render` 实现。约 20 行替代了 express-ejs-layouts 整个依赖。
3. **余额是派生值，不是真相** —— `recalcBalances()` 从 `initial_cents` + 全量流水重算。幂等，导入/编辑/删除后都调一次。宁可慢也不会算错。
4. **统计口径明确**（`txn.js:8-10`）—— 转账 / 借贷 / 投资买卖**不计入收支统计**，只动余额。这条口径是对的，很多记账软件在这里出错。
5. **附件两条链路共用一个模块** —— 网页端 AI 记账和开放 API `/api/open/ai/bill` 都走 `attachments.js`，注释里明确写了"避免行为分叉"。
6. **资产缓存戳拼了 mtime**（`server.js:22-28`）—— 只用版本号会在"版本没变但文件改了"时继续命中浏览器缓存，注释里点名了"换头像按钮无反应"这个真实 bug。

## 三、已实证的缺陷（3 个，都是真 bug，不是猜测）

> **状态：P0 部分已于 2026-10-09 全部修复**，修复记录见文末「优化优先级」章节。
> 以下保留原始缺陷描述，供追溯。

以下每条都用一次性探针脚本在真实 `node:sqlite` 上跑出来过，脚本在 `F:\workbuddy\processing\homeledger_probe.js`。

### 🔴 缺陷 1：批量删除 / 批量报销直接抛异常，功能不可用

**位置**：`src/lib/txn.js:240-246`（`bulkDelete`）、`src/lib/txn.js:256-271`（`markReimbursed`）

```js
function bulkDelete(ids, ledgerId) {
  let n = 0;
  tx(() => {                              // ← 开事务
    for (const id of ids) if (softDelete(Number(id), ledgerId)) n++;
  });                                     //   softDelete → recalcBalances → tx() → 再开事务
  return n;
}
```

`softDelete()` 内部会调 `recalcBalances()`，而 `recalcBalances()` 用 `tx()` 包了写操作。SQLite 不支持嵌套事务，直接抛：

```
Error: cannot start a transaction within a transaction
```

`markReimbursed()` 是同一个病：`tx()` 里调 `createTransaction()`，后者又调 `recalcBalances()`。

**实测输出**：
```
[探针1] bulkDelete(3 笔) —— softDelete 内部会 recalcBalances→tx()
[探针1] ❌ 抛异常：cannot start a transaction within a transaction
```

**影响面**：
- `POST /transactions/bulk` 的 `action=delete` → 账单明细页勾选后批量删除，**100% 失败**
- `POST /transactions/bulk` 的 `action=reimburse` → 批量报销，**100% 失败**
- 两个入口都有 `try/catch` 兜底（`transactions.js:203-209` 会 `res.flash('error', ...)`），所以不会 500 崩服务，但用户看到的是"操作失败"，且**第一笔已经写进去了、后面的没写**（外层事务被内层抛异常打断时的行为取决于 SQLite 状态，实际上 `tx()` 的 catch 会 ROLLBACK，所以是全回滚）—— 属于"功能完全不可用"级别。
- 注意：`test/` 下 7 个套件**没有一个覆盖 bulk delete / reimburse**，所以回归全绿掩盖了这个缺陷。这就是"测试覆盖率看着很好但漏了主干"的典型样本。

**修复方向**（三选一，最小改动优先）：
- A：让 `db.tx()` 支持重入 —— 记录 `txDepth`，`>0` 时直接执行函数不开 `BEGIN`。改动最小（约 5 行），且一次性解决所有嵌套场景。
- B：给 `softDelete` / `createTransaction` 加 `skipRecalc` 参数，`bulkDelete` 内层传 `true`，事务结束后统一重算一次。改动稍大但语义更清晰。
- C：把 `recalcBalances` 移出 `tx()`（它内部本来就有自己的 `tx`）—— 不行，`softDelete` 里还有别的写。

推荐 **A**，顺带补一条覆盖 bulk 的回归用例。

### 🔴 缺陷 2：周期账单非自动模式会重复记账

**位置**：`src/lib/scheduler.js:64-79`

```js
if (rule.auto_post) {
  run('UPDATE recurring_rules SET last_run_at=?, next_run_at=? ...', ...advanceDate(...));
}
// 非自动模式：只提醒
for (const uid of ledgerWriterIds(rule.ledger_id)) { notify(...); }
run('UPDATE recurring_rules SET last_run_at = ? WHERE id = ?', nowStr(), rule.id);
// ↑ 只更新 last_run_at，next_run_at 原封不动
```

`auto_post=0`（只提醒不自动记账）的规则，`next_run_at` **永远不推进**。而 `runDueRecurring` 的取数条件是 `next_run_at <= today`，调度器每 30 分钟跑一次 → **同一期反复触发、反复生成交易、反复发通知**。

**实测输出**：
```
[探针3] 第一次跑生成 1 笔，第二次跑生成 1 笔
[探针3] next_run_at=2026-10-01（未推进→每次调度都会再跑一遍）
```

顺带一个更严重的问题：`tx()` 里**不管 `auto_post` 与否都执行了 INSERT**（`scheduler.js:52-63`）。也就是说"只提醒不记账"这个开关根本没生效 —— 交易照样入库，只是额外多发一条通知。代码注释和实际行为不一致。

**修复方向**：`auto_post=0` 的语义应该是"不生成交易，只提醒，且把 `next_run_at` 推进到下一期"。需要把 INSERT 包进 `if (rule.auto_post)`，并让两个分支都推进 `next_run_at`。

### 🟡 缺陷 3：`scheduler.js` 读了一个不存在的列，静默回退到 user_id=1

**位置**：`src/lib/scheduler.js:59`

```js
payload.user_id || rule.created_by_user_id || 1,
```

`recurring_rules` 表（`db.js:257-271`）**没有 `created_by_user_id` 这一列**。`db.js:314` 那个 `created_by_user_id` 是 `subscriptions` 表的。

**实测输出**：
```
[探针2] 列 = id,ledger_id,name,payload,frequency,interval_n,day_of_month,weekday,
            next_run_at,last_run_at,auto_post,is_active,created_at
[探针2] scheduler.js 读取 rule.created_by_user_id → ❌ 不存在，恒为 undefined，回退 user_id=1
```

因为 `node:sqlite` 返回的是行对象、缺列就是 `undefined` 而不报错，所以**静默**回退到 `user_id = 1`。

**影响**：周期账单自动生成的所有交易，记账人恒为 id=1。在多用户账本里，会导致"成员维度报表"数据全归到第一个用户头上；而且如果 id=1 不是本账本成员，`memberBreakdown` 统计直接漏掉这些记录。审计上也是错的。

**修复方向**：给 `recurring_rules` 加 `created_by_user_id INTEGER` 列（走已有的 `ensureColumn` 幂等迁移机制），并在 `routes/planning.js` 创建规则时写入当前用户 id。

## 四、性能画像（实测数字）

探针在 2000 笔流水的账本上量过：

| 操作 | 耗时 | 说明 |
| --- | --- | --- |
| 插入 2000 笔（裸 SQL） | 2137 ms | 约 1 ms/笔 |
| 单次 `recalcBalances()` | 25 ms | 全表 `SELECT *` + JS 逐条 `txnEffects` |
| 「记一笔」完整链路 | 27 ms | = recalcBalances + syncDebts |
| 连续 20 笔记账 | 471 ms | 约 23 ms/笔 |

**判断**：**当前规模完全够用**。家庭记账 realistically 一年几千到几万笔，25 ms 的全量重算在 1 万笔时约 100 ms，交互无感。

**但有三个随数据量线性恶化的点**，做优化时值得优先考虑：

1. **`recalcBalances` 每次记一笔都全表重算**（`db.js:663`）—— O(n) per write，n 笔就是 O(n²)。改成增量（在 `txnEffects` 基础上对 `delta` 直接 `UPDATE accounts.balance_cents`）能把单笔成本降到 O(1)。
2. **`syncDebts` 每次记一笔都 `DELETE` + 重建整张 `debts` 表**（`txn.js:352-362`）—— 而且是"先删后插"，中间有一个**空窗**：如果这一步中途失败，`debts` 表会留空。更稳妥的是 upsert + 只删过期行。
3. **`recalcBalances` 里的 `SELECT *`** —— 只需要 6 个字段（`txnEffects` 用到 type / amount_base_cents / account_id / to_account_id），`*` 会把 `note`、`ai_json` 这些长文本也读进内存。

**CSV 导出上限**：`admin.js:552-558` 用 `pageSize: 200` 循环翻页，硬上限 `page > 100` → **最多导出 2 万条**。超过就静默截断，没有任何提示。账本超过 2 万笔时用户会拿到不完整的 CSV 却不知道。

## 五、安全审查

### 已做对的

- **密码**：scrypt（N=16384, r=8, p=1, keylen=64）+ 16 字节随机盐，`timingSafeEqual` 定时安全比较（`auth.js:11-28`）
- **会话**：存 SQLite，重启不掉线；`httpOnly` + `sameSite=lax`；过期会话有定时清理
- **CSRF**：全站写操作强制校验，支持表单 `_csrf` 与 `x-csrf-token` 头
- **RBAC**：四档角色（viewer/member/admin/owner）在**服务端**强制校验
- **API 令牌**：只存 SHA-256 摘要，明文只展示一次，可吊销即时生效
- **开放 API 不走会话与 CSRF**：挂载在 `csrfProtect` 之前，用 Bearer 鉴权 —— 顺序正确
- **附件目录穿越防护**：`resolveFile()` 做了 `abs.startsWith(root + path.sep)` 校验（`attachments.js:160-162`）
- **登录限流**：按 `ip|username` 计数，10 次失败锁 10 分钟

### 需要注意的风险点

| 项 | 现状 | 建议 |
| --- | --- | --- |
| **默认密码** | `admin888`，且 `bootstrapAdmin` 会**把明文密码打印到控制台** | 部署后立刻改。若用 Docker 且没设 `ADMIN_PASSWORD`，等同裸奔 |
| **SESSION_SECRET 默认值** | `'homeledger-dev-secret-please-change'` 硬编码在 `server.js:72` | 不改的话任何人都能伪造 session cookie。README 提了但没强制 |
| **COOKIE_SECURE 默认 false** | 局域网 HTTP 场景合理 | 若公网暴露必须设 true + 反代 HTTPS |
| **express 30mb body 限制** | `server.js:63-64` urlencoded 和 json 都是 `30mb` | 为了 base64 截图方便，但 30mb 偏大，且**未登录用户也能发 30mb 请求**到 `/login`（csrf 在后但 body 解析在前）→ 轻微 DoS 面 |
| **`trust proxy: true` 无条件信任** | `server.js:59` | 限流按 `req.ip` 算，无条件信任 XFF 意味着**攻击者可以伪造 IP 绕过限流**。应改为 `trust proxy` 从 env 读，默认 false |
| **用户注册开关** | `ALLOW_REGISTER` 默认 **true** | 局域网共享场景下，任何知道地址的人都能注册。部署后建议改 false |
| **AI 配置存明文** | `settings` 表存 `ai.api_key` 明文 | 备份 `.db` 文件即等于泄露 API Key。文档里应明示 |
| **`security.force_https` 设置项** | 在 `DEFAULT_SETTINGS` 里定义了 | grep 全仓库**没有任何地方读取它** —— 是个死设置 |

## 六、可维护性观察

## 九、部署形态

- **Docker**：`Dockerfile` 基于 `node:22-slim`，非 root（`USER node`），`VOLUME /data`，带 HEALTHCHECK
- **docker-compose**：仓库自带，指向 `build: .` 本地构建；README 推荐的是预构建镜像
- **飞牛 fnOS 原生包**：`packaging/fpk/` 可打出 `.fpk`，数据存 `TRIM_PKGVAR/data`，**升级要直接覆盖安装，不要先卸载**
- **CI**：`.github/workflows/docker-publish.yml` 推 GHCR，多架构（linux/amd64 + arm64），`v*` tag + 手动 dispatch
